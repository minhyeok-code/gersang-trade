# 거상 트레이드 부하테스트 리포트

> 문제 발견 → 진단 → 해결 → 수치 변화 (로컬 + 운영)
> 최종 갱신: 2026-08-10

---

## 1. 개요

거래 목록(`/api/listings`)과 계산기(`/api/calculator`, `/api/calculator/dps`)를 대상으로 부하테스트를 진행했다. 목적은 "몇 명까지 감당하는가"가 아니라 **어디서·왜·어느 지점에서 무너지는가**를 찾는 것. 테스트 과정에서 성능 병목과 데이터 무결성 문제 여러 개가 드러났고 모두 해결했다.

## 2. 도구 & 환경

- **부하 생성**: k6 (VU = 가상 사용자, `sleep(1)` think-time)
- **모니터링**: Spring Boot Actuator + Micrometer → Prometheus → Grafana
- **관측 지표**: 요청률(RPS), 응답시간 p95/p99, 에러율, HikariCP 커넥션 풀, JVM 힙, Repository 호출률
- **로컬**: 앱·MySQL·Prometheus·Grafana·k6를 단일 PC에서 실행
- **운영**: k6 전용 EC2 → 앱 EC2(nginx→Spring→MySQL). k6와 앱을 물리적으로 분리, 같은 리전. Cloudflare 미경유, 공인 IP로 HTTP 직접 부하

## 3. 로컬 단계 — 성능 병목 2개

### 문제 1 — 과도한 SQL 로깅
- **발견**: 95 VU에서 실패율 63.68%, p95 1.55초, 앱이 2분 만에 크래시
- **진단**: `application-local.yml`의 `org.hibernate.SQL=DEBUG`, `bind=TRACE`가 부하 시 쿼리마다 전체 SQL+파라미터를 출력 → 메모리·I/O 폭발
- **해결**: 로그 레벨 WARN (부하테스트용 `loadtest` 프로필 분리)

| 지표 | Before | After |
|---|---|---|
| p95 | 1.55초 | **87ms** |
| 실패율 | 63.68% | **0%** |
| 앱 | 2분 만에 크래시 | 완주 |

### 문제 2 — DPS N+1 → DB 커넥션 풀 고갈
- **발견**: 로깅 끈 뒤 dps 스트레스(200~400 VU)에서 서버 다운, DPS p95 30초, 실패율 71%
- **진단**: 서브 계산기(`AwakenedMyungwangBuffCalculator` 등)가 특성마다 `findByCharacteristicId`를 개별 조회하는 N+1. `@Transactional`이 계산 전체를 감싸 커넥션 장기 점유 → 풀 10개 고갈 → 189개 대기 → 30초 타임아웃
- **해결**: 정적 카탈로그(용병 특성·특성 레벨) `@Cacheable` + 관리자 편집 시 `@CacheEvict`

| 지표 | Before | After |
|---|---|---|
| DPS p95 | 30초 | **843ms** |
| 실패율 | 71.47% | **0%** |
| 앱 | 다운 | 400 VU 6분 완주 |

## 4. 운영 단계 — 데이터 무결성 문제 + 계산기 캐싱

운영 배포 후 부하테스트에서 **잠복해 있던 실제 버그 3개**가 드러났다. 일반 사용만 했으면 언젠가 유저가 겪었을 것들.

### 문제 3 — `set_granted_skills` skill_key 중복 → 앱 기동 실패
- **발견**: 배포 시 앱-green이 기동 실패, 롤백. 로그: `NonUniqueResultException ... SetGrantedSkillSeeder`
- **원인**: `skill_key`에 유니크 제약 없음 + 블루-그린 동시 시딩 경쟁으로 중복 삽입
- **해결(파이프라인)**: Flyway `V4` 마이그레이션으로 중복 정리 + UNIQUE 제약 추가, 시더도 `existsBySkillKey` + 예외 내성으로 강건화

### 문제 4 — 고아 데이터 → 계산기/DPS 500
- **발견**: 계산기 stress에서 실패율 100%. 단건 curl → HTTP 500. 로그: `EntityNotFoundException: Unable to find Mercenary with id 385`
- **원인**: 존재하지 않는 용병을 가리키는 고아 행 (`mercenary_stats`, `legend_general`, `player_character_detail`)
- **해결(데이터)**: 아래 §6의 수동 SQL로 고아 제거
- **해결(코드)**: `MercenaryStatRepository.findByStatKey`에 `JOIN FETCH mercenary`(inner join) 추가 → 고아 스탯을 결과에서 자동 제외해 재발 방지

### 문제 5 — 계산기 미캐싱 → 고부하 p95 급등
- **발견**: 고아 수정 후 calculator stress(400 VU) 성공했으나 p95 2.85초
- **원인**: `mercenary_stats`·`item_stats`를 요청마다 캐시 없이 DB 조회
- **해결**: 두 조회 메서드 `@Cacheable`(용병 스탯은 fetch join으로 캐시 안전 보장) + 관리자 스탯 수정 시 `@CacheEvict`

| 지표 (calculator, 400 VU) | 캐싱 전 | 캐싱 후 |
|---|---|---|
| p95 | 2.85초 | **5.26ms** (약 540배 ↓) |
| p99 | 4.2초 | 10.4ms |
| 처리량 | 81 req/s | **178 req/s** |
| 실패율 | 0% | 0% |

## 5. 운영 최종 결과

동일 stress(400 VU, 6분). 400 VU는 현실 트래픽보다 훨씬 공격적(k6 think-time 1초 ≈ 실제 유저 20~30명분).

| 엔드포인트 | p95 | p99 | 실패율 |
|---|---|---|---|
| `/api/listings` | 13ms | 21ms | 0% |
| `/api/calculator` | 5.26ms | 10.4ms | 0% |

**수용력 판단**: 이벤트 참여자 약 8,000명 기준 가입자 1만 명 가정 시, 실제 peak 동시접속은 수십~수백 명 수준. 위 결과(400 공격적 VU를 한 자릿수 ms로 처리)로 볼 때 **평상시 트래픽은 충분히 여유**. 이벤트성 급증만 spike 프로파일로 별도 점검 권장.

## 6. 운영 데이터 정리 기록 (수동 SQL)

일회성·환경 특정 데이터 오염이라 Flyway 대신 수동 정리. 추적성 확보를 위해 실행 SQL을 여기 기록한다. (2026-08-10 운영 DB)

```sql
-- (1) mercenary_stats 고아 제거
DELETE ms FROM mercenary_stats ms
  LEFT JOIN mercenaries m ON ms.mercenary_id = m.id
  WHERE ms.mercenary_id IS NOT NULL AND m.id IS NULL;

-- (2) legend_general 고아: 손자 → 자식 → 본체 순
DELETE ce FROM characteristic_effects ce
  JOIN legend_general_characteristic c ON ce.characteristic_id = c.id
  JOIN legend_general lg ON c.legend_general_id = lg.id
  LEFT JOIN mercenaries m ON lg.mercenary_id = m.id
  WHERE lg.mercenary_id IS NOT NULL AND m.id IS NULL;
DELETE c FROM legend_general_characteristic c
  JOIN legend_general lg ON c.legend_general_id = lg.id
  LEFT JOIN mercenaries m ON lg.mercenary_id = m.id
  WHERE lg.mercenary_id IS NOT NULL AND m.id IS NULL;
DELETE p FROM legend_general_passive p
  JOIN legend_general lg ON p.legend_general_id = lg.id
  LEFT JOIN mercenaries m ON lg.mercenary_id = m.id
  WHERE lg.mercenary_id IS NOT NULL AND m.id IS NULL;
DELETE lg FROM legend_general lg
  LEFT JOIN mercenaries m ON lg.mercenary_id = m.id
  WHERE lg.mercenary_id IS NOT NULL AND m.id IS NULL;

-- (3) player_character_detail 고아 제거
DELETE t FROM player_character_detail t
  LEFT JOIN mercenaries m ON t.mercenary_id = m.id
  WHERE t.mercenary_id IS NOT NULL AND m.id IS NULL;
```

## 7. 변경 파일 요약

**모니터링 연동**: `build.gradle`(micrometer-prometheus), `application.yml`(actuator 노출·히스토그램·cache-names), `application-loadtest.yml`(신규)

**성능 수정**: `CacheConfig`(캐시 상수), 리포지토리 `@Cacheable`(특성/레벨·아이템스탯/용병스탯), `MercenaryAdminService`·`ItemAdminService`(@CacheEvict), `MercenaryStatRepository`(fetch join)

**배포 강건화**: `deploy.yml`·`deploy.sh` — `git pull` → `git fetch + reset --hard origin/main` (서버 로컬 드리프트에 배포가 막히지 않도록)

**부하 하네스** (`loadtest/`): k6 스크립트, payload, 모니터링 스택(로컬·운영)

## 8. 배운 것 / 운영 원칙

- **운영 서버를 직접 수정하지 않는다.** 모든 설정·코드 변경은 레포 → 커밋 → 파이프라인 배포로 흘려보낸다. (이번에 prometheus 설정을 서버에서 직접 `sed`로 고친 게 git 충돌·배포 실패를 유발함)
- 서버에서 하는 건 **읽기 전용 진단**만(`docker ps`/`logs`, `curl`).
- **스키마·재현 대상 데이터 → Flyway. 환경 특정 일회성 데이터 오염 → 수동 정리 + 기록**(§6).
- 부하테스트는 성능 측정을 넘어 **잠복 버그 발견 도구**로 큰 값어치를 함(이번에 3개 발견·해결).

## 추신(P.S.) — 커넥션 풀은 왜 무작정 안 늘리는가

- DB 커넥션은 MySQL 쪽 메모리·스레드를 소비. 무작정 열면 `max_connections`에 걸려 DB가 먼저 죽음.
- 실제 병렬 처리량은 DB의 CPU·디스크로 정해짐 → 커넥션만 늘리면 경합·컨텍스트 스위칭으로 오히려 느려짐.
- 풀이 차서 대기하는 건 DB를 보호하는 방어벽. HikariCP 권장: `(코어수 × 2) + 디스크수`.
- **이번 사례가 증명**: 로컬/운영 모두 커넥션 풀을 10 그대로 두고, 진범(N+1·미캐싱)을 캐싱으로 잡으니 400 VU를 한 자릿수 ms로 처리. 풀이 아니라 **요청당 DB 작업량**이 문제였다.
